# App Store Screenshots Playbook

How an app's marketing screenshots are **composed, verified and uploaded**. The whole set should be generated by scripts—nothing is hand-edited in an image editor, and **no marketing pixel is ever retouched**.

- Generator: `scripts/make_frames.py` (or equivalent)
- Delivered set: `output/screenshots/`
- Uploader: `scripts/upload_screenshots.sh`
- Capture provenance: Document your capture states in a `README.md`
- Field limits: Refer to Apple's App Store Connect guidelines for `screenshotDisplayType` enumerations.

```sh
python3 scripts/make_frames.py          # rewrites output/
ASC_KEY_ID=... ASC_ISSUER_ID=... ./scripts/upload_screenshots.sh
```

---

## Invariants — do not break these

- **Target correct dimensions, RGB, no alpha, square outer canvas corners, PNG.** Ensure your primary set covers the required sizes (e.g., 1290×2796 for largest iPhones). If ASC API lacks a specific bucket for a newer device size, fall back to the largest supported. Verify with `sips -g pixelWidth -g pixelHeight -g hasAlpha`.
- **Every capture is from the app's PREMIUM (unlocked) state.** Hard requirement: **no frame may show** a paywall, an upgrade / unlock / trial CTA, `Restore Purchases`, a price, a locked feature, a hit free-tier cap, or any debug UI.
- **No caption may say "transparent" / "see-through" / "clear" / "invisible" when describing native iOS features that don't support it.** Describe the *outcome* visually. Search keywords belong in the ASC keywords field and are never displayed on images. This is deliberate rejection-risk reduction.
- **Every claim must be literally true and sourced from the running app.** Counts must come from real analytics. **No invented social proof** — no fake ratings, awards, user counts or "#1" badges (App Store Review Guidelines 2.3.1 / 3.2.2(i)).
- **Never upscale a source render.** Every tile or device screen is placed at ≤ its native captured pixel size.
- **Never composite a native OS element (like a widget) onto a photo to fake host transparency or behaviors.** Arranging *real* renders into a marketing composition is legitimate; faking the effect is not.
- **Raw captures should not be committed.** Store them in ignored local folders. If they are lost, the frames cannot be re-rendered without redoing the whole simulator capture session. Document the simulator states carefully.

## The Set Structure

A typical screenshot set might look like this, defined by numeric prefixes to control App Store display order:

| # | File | Treatment | Shows |
|---|------|-----------|-------|
| 1 | `01-showcase.png` | showcase | Tilted phone + real UI elements scattered around it |
| 2 | `02-feature.png` | showcase, no phone | Real UI components floating with content highlighted |
| 3 | `03-home.png` | device | Primary screen, upright in a device body |
| 4 | `04-gallery.png` | device | Browsing experience or catalog |
| 5 | `05-settings.png` | card | Scrolled list or settings, masked to a card |

Frames are emitted in passes (e.g., Showcase → Device → Card). **Output order is the App Store display order**, which the upload script derives by sorting on filename — so the numeric prefixes are load-bearing.

---

## The Three Treatments

**Showcase** — caption over a branded background, an optionally tilted phone body, and a scatter of UI tiles pasted with rotations. Tile specs usually require `(file, cx, cy, width, angle[, trim])`.

**Device** — the capture wrapped in a device body mockup: a hardware body with a squircle outer edge, a **concentric** screen (`screen_r = body_r - bezel`), a metal rim highlight, side buttons and a drop shadow.

**Card** — the capture masked to a plain rounded inset with a hairline border and shadow. Used for scrolled or sliced content.

### Which capture may wear a device body

**Only a capture that still has its real status bar and Dynamic Island/Notch.** A body implies a whole phone; if the capture's top was cropped away, the top bezel sits above content that starts mid-screen and it reads as a rendering glitch.

- Uncropped primary screens → device (`crop_top = 0`).
- Scrolled lists or deeply pushed views → **card**, because their captures are sliced.

> ⛔️ **Always watch for stale copy.** Captures that show "Restore Purchases" or deprecated marketing claims must be cropped or recaptured.

## Corner Geometry — the part that is easy to get wrong

Every rounded corner should be a continuous **squircle** (superellipse), `|dx/r|^n + |dy/r|^n ≤ 1`, built at **4× supersample then LANCZOS** so the curve is clean rather than stair-stepped. A plain circular-arc rounded rectangle reads subtly wrong next to real Apple hardware.

Use variables to control geometry:

| Constant | Default | What |
|---|---|---|
| `BODY_R_RATIO` | `0.152` | Phone body corner, as a fraction of body width. Screen corner is derived concentrically. |
| `CARD_R_RATIO` | `0.14` | Plain rounded inset corner (card treatment). |
| `SQ_N` | `4.8` | Superellipse exponent for bodies and cards. |

> ⚠️ **The exponent — not the radius — controls perceived roundness.** At `n = 4.8` the edge stays flat almost to the corner and then turns sharply, which reads *square* no matter how large the radius. Lowering `n` is the knob that actually works.

> ⚠️ **Native UI elements require tight squircles.** iOS's own widgets and icons use specific exponents. If you apply a global squircle function, ensure native-looking floating tiles still use their proper exponent so they look like real iOS elements.

**Concentric screen corners are the single most common tell of a fake mockup.** Always zoom into a corner of a final PNG before shipping.

## Traps to Avoid

- **Designs with outer glows or shadows need trimming.** If a UI card has its own shadow, masking the raw capture to a card corner leaves artifacts. Crop source pixels off every edge **before** masking.
- **Luminance floors must clear dark backgrounds.** When keying out backgrounds (like dark mode wallpapers), ensure the threshold fully drops the background without ghosting.
- **Manage background bloom.** If using a background gradient or bloom, ensure it extends down far enough. A short card placed low might land in a dead black region if the bloom decays too early. Add secondary lower blooms if needed.
- **A short crop must not be vertically centred.** It floats in the middle and leaves a dead band under the caption that reads as a layout mistake at thumbnail size. Bias crops upwards.
- **Two frames of the same screen must differ at thumbnail size.** If two screenshots use the same base view, ensure their hero content differs drastically (e.g., completely different data or state).
- **Captures can go stale against the shipped binary.** If a feature is renamed, recapturing is required. Do not retouch the pixels, as that violates the honesty rule.
- **Never show placeholder data when advertising real features.** If an API returns deterministic placeholders in the simulator, do not use them if they misrepresent the live app. Inject realistic mock data during capture.

## Verification Before Upload

Do all of this manually — **do not trust automated checks alone**.

1. `sips -g pixelWidth -g pixelHeight -g hasAlpha` on every PNG → Ensure correct dimensions and no alpha.
2. **Open every frame** downscaled (≈⅓) to judge it at thumbnail size.
3. **Zoom into all four corners** of at least one device frame at full resolution — check the concentric screen corner, the bezel and the side rails.
4. Re-read the Premium-state checklist above against each frame.
5. `git status` — confirm nothing else changed.

Upload scripts typically replace the whole set. Read the final API response: wrong dimensions are *not always* rejected at upload time; they surface later in processing errors. Re-poll the set and confirm every entry is `COMPLETE` with no errors before considering it done.

```sh
# Example verification using the App Store Connect API
curl -X GET "https://api.appstoreconnect.apple.com/v1/appScreenshotSets/<setId>/appScreenshots?limit=50" -H "Authorization: Bearer \$TOKEN"
```
